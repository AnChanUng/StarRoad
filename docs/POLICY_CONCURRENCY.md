# 정책 상담 동시성 처리

기존에는 Python의 전역 잠금이 상담 한 건을 실행하는 동안 모든 다른 상담을 429로 거절했습니다.
이제 상담은 작업으로 접수하고, 화면이 작업 상태를 조회합니다.

## 요청 흐름

1. 브라우저가 요청 번호를 생성하고 `POST /starroad/policy/ai/jobs`에 질문을 제출합니다.
2. Spring이 CSRF·질문 형식을 검사하고, 서버 세션에 보관한 소유자 ID와 함께 Python에 전달합니다.
3. Python은 202와 작업 ID를 반환합니다. 상태는 queued → running → succeeded 또는 failed입니다.
4. 화면은 `GET /starroad/policy/ai/jobs/{id}`를 1초 간격으로 조회합니다.
5. 완료되면 기존 답변·출처·검증 상태를 표시합니다. 연결이 끊기면 같은 요청을 재접수하거나 기존 작업을 다시 조회합니다.

## 제어 범위

| 항목 | 구현 |
| --- | --- |
| 실행 제한 | 단일 Python 프로세스, 작업 스레드 2개 |
| 접수 제한 | 실행·대기 합계 최대 32건, 세션당 미완료 작업 1건 |
| 같은 정책 | 색인 수정부터 답변 생성까지 동시에 실행하지 않음 |
| 다른 정책 | 사용 가능한 작업 스레드에서 최대 2건 병렬 처리 |
| 대기열 | 같은 정책이 실행 중이면 해당 대기 작업을 건너뛰어 다른 정책을 처리 |
| 중복 제출 | 소유자 ID + 요청 번호가 같으면 기존 작업 ID 반환. 내용이 다르면 409 |
| 결과 보호 | 요청 헤더의 임의 소유자 ID를 신뢰하지 않고 Spring 세션의 ID 사용. 다른 소유자 조회는 404 |
| 결과 보관 | 완료 후 15분, 최대 512건. 보관 공간도 가득 차면 새 작업을 429로 거절 |
| 공유 자원 | 서비스/스케줄러/모델/색인/그래프 초기화 보호, 공용 임베딩·캐시 접근 직렬화 |
| 기존 동기 API | 같은 작업 대기열을 사용. 새 화면은 작업 API를 사용 |

질문과 과거 대화는 작업이 완료되면 작업 객체에서 제거합니다. 응답은 조회를 위해 보관 기간 동안 메모리에 남습니다.
로그에 질문·응답·모델 키·서버 토큰을 추가로 기록하지 않습니다.
동일 요청의 재시도는 같은 번호를 사용해야 합니다. 새 번호로 제출한 요청은 새로운 상담입니다.

## 화면과 장애 처리

- 대기·처리 중 상태를 표시하고 중복 제출을 잠급니다.
- HTTP 요청은 10초에 연결 확인을 종료하지만, 서버의 작업을 취소하지는 않습니다.
- 자동 상태 조회는 한 번에 최대 5분입니다. 이후 ‘진행 상황 다시 확인’으로 같은 작업을 조회할 수 있습니다.
- 접수 응답이 유실되어 작업 ID를 못 받았어도 원래 요청 번호로 다시 제출하므로 중복 생성하지 않습니다.
- 작업 실패는 failed 상태와 일반 안내 문구로 반환하며 내부 예외는 노출하지 않습니다.
- 대기열/세션 한도 429, 요청 번호 충돌 409, 없는 작업·다른 소유자·만료 작업 404를 처리합니다.

## 보장하지 않는 범위

작업 저장소는 메모리입니다. 서버 재시작/강제 종료 시 작업·결과·중복 방지 기록이 사라집니다.
페이지를 닫거나 새로고침하면 화면의 대화와 요청 번호도 사라집니다. 이미 접수한 서버 작업은 계속 실행될 수 있습니다.
따라서 재시작을 넘는 exactly-once 처리나 새로고침 후 자동 복구를 보장하지 않습니다.
정상 종료는 대기 작업을 실패로 마감하고 실행 중인 작업이 끝나기를 기다립니다.
멈춘 모델 호출을 강제로 중단하는 기능은 없으며, 기존 모델 클라이언트의 타임아웃/재시도 정책을 사용합니다.

이 구조는 `uvicorn --workers 1` 전용입니다. 여러 프로세스/서버로 확장하려면 공유 작업 저장소,
정책별 분산 조정, 재시도/복구 정책 및 색인 저장 구조를 함께 바꿔야 합니다.
동일 데이터 폴더를 다른 CLI/Streamlit 프로세스에서 동시에 수정하면 안 됩니다.
세션 제한은 사용자 인증에 기반한 과금 한도나 악의적 트래픽 차단을 대신하지 않습니다.

## 동시 요청 검증

테스트 대역을 이용한 검증이며 실제 LLM의 처리량/지연 개선 수치는 아닙니다.

- 같은 정책의 첫 작업을 의도적으로 멈춘 동안 다음 같은 정책은 대기하고, 다른 정책은 두 번째 스레드에서 완료.
- 동일 요청 64개 동시 제출 → 작업 ID 1개, 실행 1회.
- 작업 20개를 총 80번 제출 → 실제 실행 20회, 동시 실행 최대 2건, 같은 정책의 중첩 실행 없음.
- 결과 소유권, 만료, 보관 한도, 접수 한도, 실패 후 정책 점유 해제 검증.
- 최초 동시 요청 시 스케줄러 1개만 생성되는지, 모델 초기화/임베딩 캐시 계산이 중복되지 않는지 검증.
- 브라우저에서 대기/실행/완료/실패 상태 및 접수 응답 유실 후 동일 번호 재시도 검증.

실행 명령은 기존 [전체 검증 문서](TESTING_POLICY_AI.md)를 사용합니다.
Python에는 `test_jobs.py`, `test_shared_concurrency.py`가 추가되었습니다.
